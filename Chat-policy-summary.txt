Policy Summary API — Current-State Assessment and Read-Replica-Based Policy Summary Architecture
1. Executive Summary

The existing Policy Summary API was originally designed to provide consumers with a simplified view of policy information without requiring every consumer to understand or integrate directly with the underlying policy systems.

The API maintains a Policy Summary Database, which is populated through REST calls originating from the policy source system. However, the current implementation has several significant architectural limitations:

The Policy Summary Database is populated only for Automobile policies.
It does not currently provide Property policy information.
It does not contain policy information originating from mainframe systems.
In many consumer scenarios, the Policy Summary API ultimately retrieves information from the source system at runtime.
Guidewire's REST call to the Policy Summary API introduces tight coupling between the Policy System and the Policy Summary capability.
The architecture creates a dependency on the availability, performance, scalability, and release cycles of the source systems.
The Policy Summary Database is therefore not functioning as a true enterprise policy read model; it is effectively a partial cache supplemented by runtime source-system calls.
As the number of consumers and policy domains increases, this architecture becomes increasingly difficult to scale and evolve.

The original objective of avoiding direct calls to the source system is therefore not consistently achieved.

Recommended Direction

A new Policy Summary / Policy Read Model platform should be established using read replicas and/or CDC-based data replication from all authoritative policy systems.

The new architecture should:

Obtain policy data from source-system read replicas rather than making synchronous consumer-driven calls to transactional systems.
Support Guidewire Automobile, Guidewire Property, and mainframe policy data.
Build and maintain a canonical Policy Summary representation.
Keep consumers independent from the underlying policy systems.
Decouple the lifecycle and availability of consumers from transactional policy systems.
Provide a scalable read-optimized data store for high-volume policy inquiries.
Allow the underlying policy systems to change without requiring every consumer to change.
Provide a foundation for future policy domains and additional source systems.

The proposed architecture changes the fundamental integration pattern from:

Consumer → Policy Summary API → Source System

to:

Source Systems → Read Replicas / CDC → Policy Read Model → Policy Summary API → Consumers

This is a significant improvement in separation of concerns, scalability, resiliency, and architectural flexibility.

2. Background

The Policy Summary API was introduced to provide consumers with a simplified policy representation.

The general concept was sound:

Consumers should not need to understand the internal data model of Guidewire or legacy policy systems.
Consumers should not need to establish individual integrations with each policy system.
A common API should provide a consistent policy summary.
A Policy Summary Database could potentially satisfy frequently requested policy information without repeatedly accessing transactional systems.

However, the implementation evolved in a way that does not fully achieve these objectives.

The Policy Summary Database is currently populated through REST interactions from a policy system.

For example:

Guidewire Policy System
        |
        | REST
        v
Policy Summary API
        |
        v
Policy Summary Database

At first glance, this appears to create a decoupled architecture.

However, there are two different forms of coupling involved:

Data synchronization coupling
Runtime request coupling

The second is particularly problematic.

4. Fundamental Architectural Issue
4.1 The Policy Summary Database Is Not a Complete Policy Read Model

A read model should ideally contain the information necessary to satisfy the read use cases for which it exists.

The current Policy Summary Database has limited coverage:

Policy/Data Domain	Current Coverage
Automobile policies	Yes
Property policies	No
Mainframe policies	No
Other policy systems	Limited/No
Enterprise-wide policy view	No

Consequently, consumers cannot consistently treat the Policy Summary API as an authoritative read interface across policy domains.

Instead, the API must determine whether it has the required information and, when it does not, retrieve the information from the source system.

This creates architectural complexity and inconsistent behavior.

5. Runtime Dependency on Source Systems

One of the most significant problems is the runtime dependency on the source system.

Consider the following flow:

Consumer
   |
   | GET Policy Summary

   |
   | Data not available
   v
Guidewire Policy System
   |
   v
Policy Summary API
   |
   v

The consumer believes it is interacting with the Policy Summary API.

However, from a system-dependency perspective, the consumer request is indirectly dependent on Guidewire.

Therefore:

Consumer
   |
   v
Policy Summary API
   |
   v
Guidewire

is still part of the runtime dependency chain.

This creates several problems.

Availability Coupling

If Guidewire is unavailable, degraded, undergoing maintenance, or experiencing high load, the Policy Summary API may also be unable to satisfy requests.

Therefore:

Policy Summary availability becomes dependent on source-system availability.

This defeats one of the primary reasons for introducing a read model.

6. Performance Coupling

Source systems are generally optimized for transactional policy operations.

They are not necessarily designed to handle large volumes of enterprise-wide read traffic from downstream consumers.

For example:

100 Policy Summary requests
        |
        v
Policy Summary API
        |
        v
100 requests to Guidewire

As the number of consumers increases:

Consumer A ----\
Consumer B -----\
Consumer C ------> Policy Summary API ---> Guidewire
Consumer D -----/
Consumer E ----/

the Policy Summary API can unintentionally become a traffic multiplier against the transactional system.

This can create:

Increased Guidewire CPU utilization
Increased database utilization
Increased network traffic
Increased response times
Increased connection utilization
Increased API thread utilization
Increased risk of throttling
Increased probability of cascading failures

The problem becomes more significant as additional consumers are onboarded.

7. Tight Coupling Between Guidewire and Policy Summary API

Another important architectural concern is the REST integration from Guidewire to the Policy Summary API.

Conceptually:

Guidewire
    |
    | REST
    v
Policy Summary API

This creates a dependency between two independently evolving systems.

Guidewire is now aware of the Policy Summary API as an integration dependency.

This is a form of temporal and operational coupling.

7.1 Temporal Coupling

For a synchronous REST interaction to succeed:

Guidewire must be available.
Policy Summary API must be available.
Network connectivity must be available.
Authentication must work.
The API contract must be compatible.
The Policy Summary API must respond within an acceptable time.

Therefore:

Guidewire operation
       |
       +---- Policy Summary API available?
       |
       +---- Network available?
       |
       +---- Authentication available?
       |
       +---- API responding?
       |
       +---- Contract compatible?

The source system's operation is therefore indirectly dependent on another application.

This is undesirable when the Policy Summary capability is not part of the core transactional operation.

8. Failure Propagation

Synchronous integration also creates the possibility of failure propagation.

For example:

Guidewire
   |
   | REST
   v
Policy Summary API
   |
   X

A failure in a downstream read capability can therefore affect the upstream transactional system.

This violates an important resiliency principle:

Failure of a non-critical downstream capability should not unnecessarily impact the core transactional system.

10. Consumer-Driven Coupling

The current design also creates an indirect coupling between consumers and source-system behavior.

A consumer calls:

GET /policy/{policyNumber}

but the response may depend on:

Whether the policy is present in the Policy Summary Database
Whether the policy is Automobile or Property
Whether the source system is available
Whether the source system responds within the timeout
Whether the source system supports the required operation
Whether the source system's API contract has changed

Consequently, consumers receive a common API contract but do not necessarily receive a common runtime behavior.

This makes the Policy Summary API less predictable.

The current architecture scales the read workload back to the transactional systems.

This is the wrong direction for a high-volume read use case.

The source systems do not need to process every downstream policy inquiry.

21. Eventual Consistency

The proposed architecture introduces eventual consistency, which should be explicitly acknowledged.

For example:

10:00:00
Policy updated in Guidewire

10:00:01
Change captured by CDC

10:00:02
Read Model updated

10:00:03
Consumer sees new policy state

The Policy Read Model may therefore lag the source system by a small amount.

This is an acceptable trade-off for many read-only policy summary use cases.

However, not every use case should necessarily use the Policy Read Model.

A useful architectural rule is:

Use the Policy Read Model for read/query use cases where near-real-time or eventually consistent data is acceptable. Use the transactional source system when authoritative real-time transactional state is required.

This prevents the read model from being incorrectly positioned as a replacement for the system of record.

22. Clear Separation of Responsibilities

This is substantially cleaner than having the Policy Summary API perform source-system orchestration during every request.

30. Avoiding the "Enterprise Cache" Anti-Pattern

The new solution should not simply become another cache.

There is an important distinction.

Cache

A cache generally exists to temporarily store data to improve performance.

Source System
     |
     v
    Cache
     |
     v

The source remains the primary runtime dependency.

Read Model

A read model is intentionally constructed to support specific read/query use cases.

Source Systems
     |
     | replication
     v
Policy Read Model
     |
     v
Consumers

The consumer's normal runtime path does not require the source system.

The proposed Policy Summary architecture should therefore be positioned as a Policy Read Model, not simply a cache.

31. Architectural Principles

The new solution should be governed by several principles.

Principle 1 — Source Systems Remain Systems of Record

Guidewire and mainframe systems remain authoritative for their respective policy transactions.

The read model does not replace them.

Principle 2 — Consumers Should Not Directly Depend on Source Systems

Consumers should access policy information through the Policy Summary capability.

Consumer
   |
   v
Policy Summary API

rather than:

Consumer
   |
   v
Guidewire/Mainframe
Principle 3 — No Runtime Source-System Dependency for Standard Reads

Normal Policy Summary requests should not require a synchronous call to the source system.

Preferred:

Consumer
   |
   v
Policy Summary API
   |
   v
Policy Read Model
Principle 4 — Replication Should Be Asynchronous

Source changes should be propagated asynchronously using appropriate mechanisms such as:

CDC
Replication
Events
Messaging

The exact technology can be determined independently from the architectural principle.

Principle 5 — Canonical Model at the Enterprise Boundary

Source-specific representations should be transformed into a canonical Policy model where appropriate.

Principle 6 — Eventual Consistency Must Be Explicit

Each consumer use case should have a defined data freshness requirement.

Principle 7 — Transactional Operations Remain With the Source System

The Policy Read Model should primarily support read/query workloads.

It should not become a mechanism for performing transactional policy updates.

36. Risks and Mitigations

The proposed architecture does introduce new considerations.

Risk: Eventual Consistency

Risk: The read model may temporarily lag the source system.

Mitigation: Establish explicit freshness SLAs and identify use cases that require authoritative real-time data.

Risk: Data Replication Complexity

Risk: CDC/read-replica pipelines require operational management.

Mitigation: Standardize the ingestion pattern and monitoring across source systems.

Risk: Data Transformation

Risk: Guidewire and mainframe have different data models.

Mitigation: Introduce a canonical policy model and clearly define transformation ownership.

Risk: Duplicate Data

Risk: Policy information exists in both the source system and read model.

Mitigation: Treat the source as authoritative and the read model as a derived representation.

Risk: Stale Data During Outage

Risk: If replication stops, the read model may become stale.

Mitigation: Monitor replication lag and expose operational metrics such as:

Last successful source update
Last successful replication
Current replication lag
Number of failed events
Number of records pending processing

38. Architectural Decision
Decision

Establish a new Policy Read Model / Policy Summary platform populated through read replicas and/or CDC from all applicable policy source systems, including Guidewire Automobile, Guidewire Property, and mainframe policy systems.

The Policy Summary API should read from this centralized read model rather than synchronously retrieving information from transactional source systems for normal read operations.

Rationale

The current Policy Summary implementation does not fully achieve its original objective of insulating consumers from source systems because the API frequently falls back to source-system calls.

This creates:

Tight runtime coupling
Availability dependency
Performance dependency
Scalability limitations
Failure propagation
Inconsistent latency
Limited policy-domain coverage
Increased integration complexity
Difficulty supporting legacy/mainframe data
Increased impact of future source-system modernization

The proposed read-replica-based architecture establishes a clear separation between:

Systems of Record

and

Policy Read/Consumption Services.

This allows the organization to scale policy reads independently from transactional policy systems while providing a consistent policy view across Automobile, Property, mainframe, and future policy platforms.

The key architectural argument is not simply:

"We need a new Policy Summary Database."

                 Consumers

The fundamental architectural principle is:

Do not make a consumer's read request travel through the transactional system when the requirement is to retrieve previously established policy information. Replicate the required data into a purpose-built read model and serve the consumer from that read model.

This architecture preserves the source systems as authoritative systems of record while providing a scalable, resilient, source-independent policy information layer for enterprise consumers.
